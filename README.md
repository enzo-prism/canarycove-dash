## Canonical data and identity

`data/submissions.ts` is generated by `scripts/canary-leads/cli.mjs`; never edit
it by hand. It contains both the data and the matching summary. The former
split modules are obsolete. The ignored decision manifest is
`data/private/formspree-reconciliation.json` (mode 0600).

Use immutable provider IDs when available. Official Formspree dashboard exports
omit those IDs, so their fallback is the source form, exact UTC timestamp and
normalized email. Keys are hashed. Formspree `_date` values without an offset
are UTC, including when this command runs on a Pacific-time computer.
Duplicate fallback identities, changed source hashes, missing historical rows,
unresolved classifications and invalid curated identities fail closed.

Existing presentation fields and external Typeform rows are preserved. New
rows use only supported source facts; do not infer absent guest counts or
booking status. Current corrections never authorize fuzzy identity matching.

## Obtain complete source exports

The old Mac mini reader path no longer exists after migration. Do not run the
old dirty checkout or claim its heartbeat successfully reconciled production.
Use the signed-in Formspree dashboard in the browser:

1. Open `/forms/xvzarybk/submissions`, then **Export**.
2. Select **Inbox**, **Spam**, and **JSON**. Record the independent Inbox and Spam
   totals, download the complete file, and confirm its row count equals both totals.
3. Repeat for `/forms/xqeqllek/submissions`.
4. Store downloads only in private internal scratch storage. Wrap each download:

```json
{
  "source": "formspree-dashboard-export",
  "formId": "xvzarybk",
  "exportedAt": "<actual UTC export time>",
  "complete": true,
  "expectedCount": 48,
  "inboxCount": 28,
  "spamCount": 20,
  "submissions": []
}
```

Copy the real `submissions` array; the example counts are the October 28 snapshot,
not permanent limits. The importer validates counts and form identity. A raw
array or a partial page is not a complete export. The existing canonical paged
API format and legacy reader envelope remain supported, but a future reader
must independently prove it exhausted pagination.

## Reconcile and release

Requires Node.js 24 (native TypeScript loading and module hooks).

```bash
node scripts/canary-leads/cli.mjs --contact /private/contact.json --booking /private/booking.json
```

The default is a dry run. `--write` persists new review decisions privately.
Review every unknown row as `lead`, `spam`, or an explicit `email_capture`;
never automatically classify unseen historical records from a count difference.
Then apply the reviewed manifest:

```bash
node scripts/canary-leads/cli.mjs --contact /private/contact.json --booking /private/booking.json --apply
node --test scripts/canary-leads/*.test.mjs
./node_modules/.bin/tsc --noEmit
./node_modules/.bin/next build
```

`--apply` validates the entire result before changing either output. It loads
legacy split TypeScript data safely and regenerates one canonical module.
For independently verified timestamp repairs only, `--identity-corrections`
accepts a private array of `{dashboardId, fromDate, toDate, sourceKey}`. Every
entry must match both the old curated row and exact approved source identity.
Do not reuse a correction after it has been applied.

Repeat apply with identical exports and timestamp to prove byte-level
idempotence. `delta.zeroDelta` means no new decision keys, not that the published
dashboard is current. Compare rows, all counts, source timestamp and production
readback. A source check time and the last published data snapshot are different.

Use a clean Studio checkout based on current `origin/main`, with a run lock.
Preserve unrelated working copies and any existing dirty data. Do not reset the
old Mac mini checkout. Review and release through the repository main/Vercel flow
under current user authorization. A Ready preview is not production proof.
Verify every expected ID exactly once and the summary on production before
marking reconciliation complete.

The daily `sync-canary-cove-leads` heartbeat should use this working process.
Future changed-data publication remains approval-gated; authentication or source
failures must report the blocker instead of claiming freshness.
